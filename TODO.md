## 1. Критические Уязвимости Безопасности

### 1.1. Отсутствие валидации входных данных
- **Проблема**: В функции `transcode_g723` (`sosna_udf.cpp`) отсутствует проверка размера и корректности BLOB-данных. Это может привести к переполнению буфера или обработке некорректных данных.
- **Файлы**: `sosna_udf.cpp` (строки 56-96), `test_transcode_g723.cpp` (строка 36).
- **Решение**: Добавить валидацию `bytes_read` и `max_seg_size`. Проверить корректность данных перед обработкой.

### 1.2. Риски переполнения буфера
- **Проблема**: В `sosna_udf.cpp:87` не проверяется индекс `output_idx` перед записью в буфер. В `sosna_udf.cpp:64` используется `std::memmove`, который может вызвать переполнение при неверном расчете `bytes_left`.
- **Решение**: Добавить проверку границ для `output_idx` и заменить `std::memmove` на циклический буфер.

### 1.3. Устаревшие библиотеки
- **Проблема**: Используются устаревшие библиотеки ITU-T G.723.1 (`g723_1_decoder.cpp`), которые могут содержать уязвимости.
- **Решение**: Обеспечить изоляцию состояния кодека для каждого вызова (Thread-Safety) через Критическую секцию (Windows Critical Section) под динамический контекст и задокументировать риски.

## 2. Проблемы управления памятью

### 2.1. Сырые указатели без четкой ответственности
- **Проблема**: В `sosna_udf.cpp:42-43` используются сырые указатели (`input_chunk`, `output_chunk`) без явного указания владельца. Нет RAII-оберток для управления памятью.
- **Решение**: Заменить сырые указатели на `std::vector<char>`.

### 2.2. Отсутствие умных указателей
- **Проблема**: В проекте не используются `std::unique_ptr` или `std::shared_ptr`.
- **Решение**: Память под внутренние буферы защищать через std::vector. А память под возвращаемый результат выделять строго через ib_util_malloc и передавать СУБД «сырым» указателем — InterBase сам удалит её, когда заберет данные. 

### 2.3. Использование функции ib_util_malloc
- **Проблема**: Если ваша UDF-библиотека будет вызывать функцию ib_util_malloc, тестовая программа столкнется с критической проблемой: при попытке вызвать эту функцию напрямую произойдет краш (падение) из-за Access Violation.
- **Решение**: Cоздаются две функции: внутренняя логика (чистый C++) - функция, которая делает всю грязную работу по транскодированию звука. На вход она принимает обычный указатель, а память под результат выделяет через стандартный фабричный метод (переданный как указатель на функцию) или через std::vector. Экспортируемая UDF-обертка (строго для InterBase) - тонкая функция, которую видит только СУБД. Она вызывает внутреннюю логику, но память под финальный BLOB выделяет через ib_util_malloc.

## 3. Узкие места производительности

### 3.1. Избыточные копии памяти
- **Проблема**: В `transcode_g723` выделяются большие буферы (`max_seg_size = 32768`), которые пересоздаются при каждом вызове. Использование `std::memmove` для сдвига данных (`sosna_udf.cpp:64`) снижает производительность.
- **Решение**: Заменить на циклические буферы и использовать `std::vector` для автоматического управления памятью.

### 3.2. Блокирующие вызовы
- **Проблема**: Обработка данных в `transcode_g723` (`sosna_udf.cpp:56`) синхронная и блокирующая.
- **Решение**: Это вызвано требованиями Interbase 2009 к UDF.

### 3.3. Избыточный отладочный вывод
- **Проблема**: В продакшен-коде активно используется `OutputDebugStringA` и `std::cout`.
- **Решение**: Заменить на условную компиляцию (`#ifdef DEBUG`).

- **Решение**: Привести код к единому стилю: **snake_case** для переменных/функций, **PascalCase** для типов.

### 4.2. Отсутствие документации
- **Проблема**: Критические функции (например, `transcode_g723`) не документированы.
- **Решение**: Добавить комментарии для функций, параметров и граничных случаев.

### 4.3. Избыточная сложность функций
- **Проблема**: Функция `transcode_g723` содержит 40+ строк с вложенными циклами и ручным управлением памятью.
- **Решение**: Разделить на более мелкие функции (например, `decode_frame`, `encode_pcm`, `flush_output`).
